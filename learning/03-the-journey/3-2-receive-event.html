@router.post("") /api/events というURLに POST（データ送り込み）で来たら、下の関数が動く。"" は「このrouterの根っこのURL」を意味し、ファイル冒頭の prefix="/api/events" と合わさって /api/events になります。

def create_event(payload: dict, db: DbSession) -> dict: 受け取るもの2つ：

  • payload: dict … 外から送られてきたデータ（辞書）。{"event_type": "demand_spike", "company_id": 1, ...} のような中身。
  • db: DbSession … DBとの会話窓口。FastAPI が自動で用意してくれる（仕組みは deps.py。今は「自動で来る」でOK）。

返すもの：-> dict、結果の辞書。

event = Event(...) 受け取った payload（辞書）から、Event クラスの実物を組み立てています（1-5のインスタンス生成）。 各項目を payload["..."] や payload.get("...") で取り出して詰めています。

注意payload["x"] と payload.get("x", 既定値) の違い（超重要）：

  • payload["event_type"] … キーが必ずある前提。無ければエラーで止まる。
  • payload.get("priority", "scheduled") … キーが無くてもOK。無ければ第2引数 "scheduled" を使う。

→ つまり event_type と company_id は 必須、description・priority・data は 任意、と コードが語っています。この区別を読めるのが「コードを読める」ということです。

db.add(event) → db.flush() add は「これを保存予定リストに入れる」、flush は「いったんDBに送ってIDを採番させる」。 まだ完全確定（commit）ではありません。確定は司令塔の中で行われます（3-3）。

config = load_company_config(event.company_id) 1-2で全文を読んだ関数です！ 会社IDから設定YAMLを読み込みます。 ここで「会社ごとの判断基準」が手に入ります。

result = RunComposer(db).run(event, config) 🔴 旅のハイライト

  1. RunComposer(db) … 司令塔の実物を作る（1-5）。DB窓口を渡す。
  2. .run(event, config) … その司令塔に「このイベントを、この設定で処理して」と依頼。
  3. 返ってきた結果を result に受け取る。

この1行の先で、エージェントたちが動き、CEOが判断します。次の 3-3 で、この .run() の中に潜ります。

✅ 検証ポイント

  • 検証必須キーの扱い：payload["company_id"] のような必須読み取りは、無いと500エラーになる。

AIが「入力チェック無しでいきなり読む」コードは、不正な入力で落ちやすい。

  • 検証flush と commit の違い：flush だけで「保存した」と思い込むと誤り。確定は commit。

ここでは司令塔側で commit される設計（3-3で確認）。「どこで確定するか」を追えるのが大事。

  • 検証結果の分岐が網羅的か：serialize_result は「CEODecisionか、それ以外」の2分岐。

3種類目の結末が増えたらここも直す必要がある、という依存に気づけるか。
