# 2-1 アーキテクチャ俯瞰図 — ASCT 全体は何をしているか

> このレッスンのゴール：個別のファイルを読む前に、「ASCT 全体が何を、どういう順でやるか」を
> 頭の中に地図として持つ。本編（03章）はこの地図を1区間ずつ歩く旅です。

---

## 🟣 ASCT を一言でいうと

> **「サプライチェーンに異変（イベント）が起きたとき、複数のAI担当者が打ち手を出し合い、
> CEO役がそれを見比べて、自動で決める。決めきれなければ人間に回す」エンジン。**

あなたが企画したこのプロダクトの核心は、「**人間の意思決定を、説明可能な形で自動化する**」ことです。

---

## 🔴 一番大事な流れ（これだけは覚える）

```
   ① イベント発生
        │   例：「フレッシュ野菜の需要が急増した」
        ▼
   ② 窓口が受け取る（API）
        │   src/api/routes_events.py
        ▼
   ③ 司令塔が段取りする（RunComposer）
        │   src/orchestrator/run_composer.py
        ▼
   ④ 担当エージェントを選ぶ（PluginRegistry）
        │   src/agents/__init__.py
        │   「需要急増」なら需要予測担当が呼ばれる
        ▼
   ⑤ 各エージェントが打ち手（シナリオ）を出す
        │   src/agents/demand_forecaster.py など
        │   「この案ならコストはこれくらい、信頼度はこれくらい」
        ▼
   ⑥ CEOが見比べて最終判断（CEOOrchestrator）
        │   src/orchestrator/ceo.py
        │   制約チェック → 点数づけ → 1つ選ぶ
        ▼
   ⑦ 結果をデータベースに保存
        │   決定(CEODecision) または 人間へ委ねる(EscalationRecord)
        ▼
   ⑧ 窓口が結果を返す
```

🔴 **この①〜⑧が ASCT の背骨です。** 本編03章は、まさにこの順番でファイルを1つずつ読みます。
各レッスンの番号と、上の番号がだいたい対応しています。

## 🔵 登場人物（モジュール）の役割early表

| 登場人物 | ファイル | 役割 | 人間にたとえると |
|---|---|---|---|
| **API窓口** | `api/routes_events.py` | 外部からイベントを受け付ける | 受付係 |
| **司令塔** | `orchestrator/run_composer.py` | 全体の段取りをする | 進行役・指揮者 |
| **登録係** | `agents/__init__.py` | イベントに合うエージェントを選ぶ | 人事・配置係 |
| **エージェント** | `agents/*.py`（4種類） | 専門分野の打ち手を出す | 各部門の専門家 |
| **CEO** | `orchestrator/ceo.py` | 打ち手を見比べ、最終決定する | 社長 |
| **エスカレーション** | `orchestrator/escalation.py` | 決めきれないとき人間に回す | 「これは社長でも決められません」 |
| **信頼度計算** | `orchestrator/confidence.py` | 各判断の自信度を数値化 | 「この見立ての確からしさ」 |
| **モデル群** | `models/*.py` | データの形を定義（DB） | 書類のフォーマット |
| **設定** | `configs/*.yaml` | 会社ごとの判断基準 | 社内規定 |

## 🔵 4種類のエージェント（専門家たち）

ASCT には4人の専門家がいます。それぞれ担当するイベントが違います。

| エージェント | 担当 | 反応するイベント (TRIGGERS) |
|---|---|---|
| `DemandForecaster` | 需要予測 | 需要急増・季節変動 |
| `InventoryOptimizer` | 在庫最適化 | 在庫アラート・発注トリガー |
| `LogisticsPlanner` | 物流計画 | 輸送路遮断・天候 |
| `SupplyRiskAssessor` | 供給リスク | 供給途絶 |

🟣 **実務での意味**：「需要が急増した」というイベントには需要予測担当が、
「輸送路が遮断された」には物流担当が反応します。
**イベントの種類によって、出動する専門家が自動で変わる** のがミソです。
この「自動で選ぶ」仕組みが `3-4`（PluginRegistry）の見どころです。

## 🔵 2つの結末：決定 か エスカレーション か

CEOの判断は、必ずどちらかに着地します。

```
              ┌─→ ✅ CEODecision（決定）
   CEOが判断 ─┤      自信を持って1つの打ち手を選べた
              └─→ ⚠️ EscalationRecord（エスカレーション）
                     決めきれない。人間に委ねる
```

**エスカレーションになる3つのケース**（`ceo.py` で読みます）：
1. 緊急なのに、どの案も信頼度が低すぎる（`low_confidence`）
2. 制約（予算・輸送費上限など）を満たす案が1つも無い（`no_viable_action`）
3. 上位2案の点差が小さすぎて甲乙つけがたい（`ambiguous_recommendation`）

🟣 **実務での意味**：これは「AIが暴走しない」ための安全装置です。
自信がないのに勝手に決めさせず、人間に判断を返す。あなたの企画思想そのものです。
